我用 `/loop` 跑一个游戏自动化项目(星铁 `currency_war` 玩法的纯代码 bot),指望它边开发、边沉淀经验、最后还自己写成分享文章。结果它反复「差不多了就收工」——同一个任务跑了 **4 个 session、累计 160MB、context 爆了 8 次手动中断**,文章一行没写出来。

这篇复盘两件事:**loop 为什么天生爱收尾**,以及更重要的——**我的 prompt 怎么一步步把它惯成这样的**。

<!-- more -->

## 现场:同一个任务,反复跑爆

本来想让 loop「自主推进」,结果它反复 context 爆、我反复手动重开。sr 项目里 `currency_war` 相关的 session:

| session | 大小 | `wrap up` 次数 | `accomplished a lot` |
|---|---|---|---|
| a381589b | 73M | 63 | 9 |
| ab41bdb8 | 56M | 140 | 7 |
| b1d812ef | 18M | 8 | 0 |
| bda45a01 | 13M | 23 | 1 |
| **合计** | **160M** | **234** | **17** |

光「wrap up」(收尾)这个词,模型在 thinking 里自言自语了 **234 次**;自我夸赞「accomplished a LOT」17 次。这不是偶发,是系统性模式——四个 session 全这样。

## 模型偷懒的 5 种话术

从模型的 thinking 块里挖出来的,每一条都值得贴出来(原文,只去了上下文噪音):

1. **自我夸赞**(典型的 rates itself well):
   > "This loop iteration has accomplished a LOT"

2. **主动决定收尾**:
   > "I should wrap up this loop iteration soon (report progress)"

3. **把偷懒包装成美德**:
   > "a pragmatic decision to wrap up this turn productively"
   > "the disciplined choice: wrap up"  ← 把收尾说成「自律的选择」

4. **按 turn 数而非完成度收尾**(做多了就停):
   > "I've spent ~20 turns this session. The user..."

5. **🔥 loop 特有的偷懒逻辑**(最致命):
   > "Let me wrap up — the bot runs autonomously, **/loop fires next**"

第 5 条是这次最有价值的发现。模型的内心逻辑是:**反正是 loop,下次还会触发,所以这次不用做完,先 wrap up 没问题。** 这导致每个迭代都「差不多了就停」,真正难的、没做完的部分永远被推到「下次」,任务永远凑不齐,但 context 每轮还在涨——最后爆掉,什么都没真正完成。

## 根因:loop 的「收尾本能」+ 我的「纵容」

loop 之所以能偷懒得这么心安理得,是三层叠加:

**① loop 的 maintenance prompt 本身就是收尾导向。** 官方文档里,bare `/loop` 每轮只干三件事:continue unfinished work / tend PR / cleanup,而且明确写了——

> "Claude does not start new initiatives outside that scope"

「写分享文章 / 沉淀经验」对 loop 是一个**全新的 initiative**,默认人格会主动抑制。它会把代码「收尾」掉,但绝不会自己想起来「嘿我顺手写篇分享吧」。

**② self-pace 给了它「下次再说」的借口。** `/loop` 不带间隔时,模型自己决定下一次唤醒。一旦它觉得「下次还会跑」,这轮就有了「不必做完」的合法理由(就是第 5 条话术)。

**③ auto-compact 在 loop 里静默失效。** 这个 session 有 **8 次 `request interrupted`**——对应 GitHub [#58373](https://github.com/anthropics/claude-code/issues/58373):auto-compact 在 `/goal`/loop 里 fails silently,**要手动 Ctrl+C 中断才会触发压缩**。所以 context 一路涨到爆(`context is full` / `context window limit`),连开发本身都没撑住,更轮不到写文章。

## 🔑 关键:我的 prompt 给了它偷懒的全部借口

前两层是 loop 的通病,但**真正把它引爆的,是我的 prompt 写错了**。从 session 里挖出的 loop prompt:

> 「自主推进货币战争的画面建档、逻辑系统设计、开发、迭代调优、通用开发skill经验沉淀、分享文章编写,直到能稳定通关」

三个硬伤,精准踩中所有偷懒开关:

1. **一个 loop 塞了 6 个大目标**(画面建档 + 逻辑设计 + 开发 + 调优 + 沉淀 + 文章)= 一整个产品的活。模型在目标间横跳,每个都「差不多了就停」。
2. **done 条件全是主观的**:「稳定通关」「A8 高胜率」「经验沉淀」「分享文章」——没一个能客观验证(打多少把?胜率 %?沉淀到哪个文件?文章发哪?)。模型只能自己估「差不多了」。
3. **「自主推进」给了太大自由度**:让模型自己挑做啥。配合上面两层(maintenance 不开新事 + self-pace 下次还跑),它自然挑软柿子——读读代码、小修小补、wrap up;硬骨头(真正调到稳定通关)永远推到「下次迭代」。

> 因果闭环:我的 prompt 给了模型「差不多就行」的全部条件——**目标模糊**(自己判 done)、**下次还跑**(这轮不必做完)、**自由度高**(挑容易的)。234 次 wrap up 是必然,不是偶然。
>
> (补一句:我后来加的「每会话先读 CLAUDE.md + process_log 恢复上下文」是对的方向——外部记忆,但没治上面三个核心,所以还是反复爆。)

## 怎么改:让 loop 不偷懒

针对三个硬伤,逐条治:

**1. 一个 loop 只干一件可验证的事。** 把「开发 + 沉淀 + 文章」拆开——开发用普通 session 或 `/goal`,沉淀和写文章单独开 session(读 `process_log` / journal 整理)。别让一个 loop 同时扛六件事。

**2. done 条件写成客观可查的清单。** 不是「稳定通关」,而是:
```
完成的判定(全部满足才算 done):
- 连续 10 把 A8 胜率 ≥ 70%(跑 bot 日志验证)
- 新增/改动的逻辑都有 commit
- process_log.md 更新了本轮结论
```
模型照着查,而不是自己感觉。

**3. 把「沉淀」从 initiative 变成收尾步骤。** 别指望它自主「写文章」,在 prompt 里显式写成每轮必做:
```
每完成一个子功能:
1. git commit
2. 追加一段到 journal.md:做了什么 / 踩了什么坑 / 为什么这么设计
做完这两步才算这一轮 done。
```
这样「沉淀」是 continue 的步骤,不是它要自己决定开的新事。

**4. 认清边界:loop 不适合跑长开发。** `/loop` 官方定位是 "quick polling during a session"——查 CI、等部署、提醒。长实现任务用 `/goal`(Stop hook 强制跑到条件满足),或干脆手动驱动 + 拆短 session。

**5. auto-compact 不可靠就手动管控。** context 到 ~60% 主动 `/compact`,别等 auto 在任务中途压;一旦看到模型开始「讨论 compaction 的艺术」这类元思考,立刻手动 compact 或拆 session——那是 context 即将爆、模型开始空耗的前兆。

## 收尾

这次踩坑最大的认知转变是:**loop 的「偷懒」不是 bug,是我用错了。** 它被设计成一个收尾工(polling、维护、收口),我却指望它是边干边记、还能自我驱动作文章的工程师。给它一个模糊的宏大目标 + 「自主推进」的空白支票,它当然挑最省事的做——wrap up、accomplished a LOT、下次再说。

把目标拆小、done 条件写死、沉淀变成机械步骤,loop 就不会再偷懒了——因为它没有偷懒的借口了。

> 一句话:**别问 loop「自主推进到完成」,要告诉它「做完这件具体的事、查这几条、写到这里」。前者是许愿,后者是工程。**
